# PRD: 리스트/탭 선택 페이지

- 작성일: 2026-09-02
- 작성자: prd-writer (초안) + 메인 세션 (선례 조사 반영, 사용자 확인 반영)
- 상태: 확정 — 도메인·핵심 컴포넌트 구성 결정됨. 세부 문구·라우팅은 구현 단계에서 정한다

## 배경

이 저장소는 Figma 디자인 시스템을 코드로 변환하는 하네스이며, 아직 실제 페이지가 하나도 없다
(`src/pages/` 비어 있음, 커밋 `dd5de09`에서 기존 페이지 4종이 제거됨). 현재 구현은 됐지만
어떤 페이지에서도 아직 쓰이지 않은 컴포넌트가 4개 있다: `Tab`, `TabItem`, `OSBarTopNavigation`,
`OSBarBottomNavigation`. 이 페이지는 그 4개를 처음으로 실제 화면에 조립해, 기존 컴포넌트
(`ListRadio`, `Button`, `Divider`)와 함께 동작하는지 검증하려는 목적으로 추천됐다.

**도메인 배경 — 정황 1 (추정, 미확정)** — 같은 세션에서 조회한 Figma 문서(파일
`TRPe9rr0YsxphvFjkWwaHp`, 노드 `2081:23098`)의 화면 위치 정보가 "U+ 라이프샵 > 패키지 추천 >
로그인 안내"였다. 이 파일은 이번 페이지가 조회한 Figma 파일과 다르며, 이 정황만으로는
"패키지 추천/혜택 선택"이 이 페이지의 도메인이라고 확정할 수 없다.

**도메인 배경 — 정황 2 (직접 검증됨)** — 메인 세션이 `git show dd5de09^:src/pages/Benefit/Benefit.design.md`
로 과거 `src/pages/Benefit/` 원문을 직접 조회했다. 그 결과, **거의 동일한 컴포넌트 조합으로
이미 한 번 구현되어 동작했던 선례**가 확인됐다.

| 항목 | 값 |
|---|---|
| 화면명 | Benefit — "요금제 선택" |
| Figma 소스 | 파일 `7DxkWa12fiJWOrvPIDWUcp`, 프레임 `27683:3204` "page/List" (402×874) |
| 원본 PRD | `docs/prd-list` (커밋 `dd5de09`에서 페이지와 함께 제거되어 현재 저장소에 없음) |
| 구조 | `OSBarTopNavigation` → `Header`(title="요금제 선택") → `Tab`(5G/LTE/알뜰폰) → `TextSetTitle`(size=lg) → `ListRadio`×3(요금제 목업, radiogroup) → `Button`×2(필터/선택 완료) → `OSBarBottomNavigation` |
| 제거 사유 | 커밋 메시지(`dd5de09`)에 결함·실패 언급 없음 — "화면 페이지 4종 제거 + 잔여 라우팅 정리"로, 저장소 정리 목적의 일괄 제거로 보인다. **기능 결함으로 제거됐다는 근거는 없다.** |

이 선례는 이번 페이지가 만들려는 조합(탭 + 리스트 선택 + 하단 액션)과 구조적으로 사실상
동일하다. **구조는 이 선례를 그대로 따르되, 콘텐츠는 정황 1(U+ 라이프샵 패키지 추천 —
혜택 선택)로 간다 — 사용자 결정.** 즉 탭은 "5G/LTE/알뜰폰" 대신 혜택 카테고리, 리스트는
요금제명 대신 혜택 항목이 된다. 또한 페이지 타이틀·뒤로가기를 위해 선례와 동일하게
`Header`를 `OSBarTopNavigation`과 함께 쓴다 — 사용자 결정. 이에 따라 이 페이지는 애초
추천됐던 "기존 4개 컴포넌트"에서 `Header`가 더해진 **5개 컴포넌트** 조합이 된다.

## 목표

- 기존 컴포넌트 5개(`Header`, `Tab`, `ListRadio`, `OSBarTopNavigation`/`OSBarBottomNavigation`,
  `Button`)만으로 탭 전환 + 단일 선택 리스트 + 하단 액션으로 구성된 페이지 1개를 완성한다.
  이 중 `Tab`·`TabItem`·`OSBarTopNavigation`·`OSBarBottomNavigation` 4개는 이 저장소에서
  처음 실제 화면에 쓰인다. `Header`는 페이지 타이틀·뒤로가기를 위해 선례(Benefit)와 동일하게
  추가로 포함한다 — `OSBarTopNavigation`은 상태바만 그리고 타이틀/뒤로가기를 제공하지 않는다.
- 이 저장소의 목적 3(구현 프로세스 표준화) 관점에서, 페이지 조립이 토큰 스캔·타입체크·빌드
  검증을 통과하는 상태로 만든다.
- 신규 컴포넌트를 만들지 않고도 실제 화면 하나가 완성될 수 있는지 확인한다 (재사용성 검증) —
  선례가 이미 동일한 5개 조합으로 이 목표를 달성한 적이 있어 재현 가능성이 높다.

## 비목표

- 새 컴포넌트 설계·추가. 이 페이지는 기존 5개 컴포넌트의 조립만 다룬다.
- 다중 선택, 검색·필터, 아이콘/배지가 붙은 탭 등 `Tab`·`ListRadio`가 지원하지 않는 인터랙션.
  (`Tab`은 `items: string[]` + `selectedIndex` + `onSelect`만 가지며 배지·아이콘이 없다.
  `ListRadio`는 텍스트 타이틀 한 줄짜리 단일 선택 행만 표현하고 다중 선택을 지원하지 않는다.)
- "요금제 선택"(선례의 원래 콘텐츠) 재현. 이번 페이지의 콘텐츠는 혜택 선택이다 — 구조만
  선례를 따른다.
- 실제 데이터 연동, API 호출, 백엔드 로직.
- 비즈니스 전환율 등 수치 목표 설정. 이 저장소에는 실사용자 데이터·분석 도구가 없다.
- 로그인·인증 흐름 자체 (인접 화면이지만 이 페이지의 범위가 아니다).

## 유스케이스

1. **(확정)** U+ 라이프샵 이용자가 패키지 추천 흐름 중 이 화면에 진입해, 헤더 타이틀로
   현재 화면을 인지하고, 혜택 카테고리 탭을 선택해 목록을 바꾸고, 그 카테고리에 속한 혜택
   항목 리스트 중 하나를 라디오로 선택한 뒤, 하단 버튼으로 다음 단계로 진행하거나 헤더의
   뒤로가기로 이전 화면에 복귀한다.
2. **(저장소 성격상 확정)** 이 저장소로 작업하는 개발자·디자이너가, 지금까지 개별적으로만
   검증됐던 `Header`·`Tab`·`ListRadio`·`OSBarTopNavigation`·`OSBarBottomNavigation`을 하나의
   화면에 조립했을 때 레이아웃·포커스 이동·토큰 사용이 의도대로 동작하는지 확인한다.

## 요구사항

### P0 — 필수

- 상단에 `OSBarTopNavigation`(상태바) + `Header`(타이틀 + 뒤로가기)를 배치한다. 뒤로가기는
  이전 화면으로 복귀한다 (선례는 `navigate(-1)`을 썼다).
- 탭 UI로 혜택 카테고리를 전환할 수 있다. 탭은 텍스트 라벨만 표시한다 (`Tab`이 배지·아이콘을
  지원하지 않으므로 이 범위를 넘는 표현은 요구하지 않는다).
- 선택된 카테고리에 속한 혜택 항목들을 리스트 행(`ListRadio`)으로 보여주고, 각 행은 제목
  텍스트 하나만 표현한다.
- 리스트 항목은 단일 선택만 가능하다. 선택 상태·선택 항목 간 상호배타 로직은 페이지가
  책임진다 (`ListRadio` 자체는 라디오 그룹 의미론이나 키보드 조작을 갖지 않는 개별 행이다).
- 하단에 확인/다음 진행용 주요 액션 버튼을 배치한다 (`Button`). 선택된 항목이 없으면
  비활성 상태로 둔다 (선례와 동일한 패턴).
- 하단에 `OSBarBottomNavigation`(홈 인디케이터)을 배치한다.
- 키보드만으로 탭 간 이동과 리스트 항목 선택이 가능해야 하고, 포커스 위치가 시각적으로
  구분돼야 한다. (정확한 role/aria 구현 방식은 구현 단계(`/new-component`)에서 정한다 — 이
  PRD는 "가능해야 한다"는 요구만 명시한다.)
- 신규 컴포넌트를 만들지 않고 기존 5개 컴포넌트(`Header`, `Tab`, `ListRadio`,
  `OSBarTopNavigation`, `OSBarBottomNavigation`, `Button`)만으로 조립을 완료한다.

### P1 — 중요, 확인 후 확정

- 탭 개수·라벨, 리스트 항목 개수·문구 등 실제 혜택 콘텐츠 — 실제 데이터가 없어 목업이 될
  수밖에 없다 (선례도 `MOCK_PLANS` 목업을 썼다). 실제 상품/혜택명을 지어내지 않고, 구현
  단계에서 "카테고리 A/B/C" 같은 자리표시자를 쓸지 최소한의 그럴듯한 목업을 쓸지는 확인
  필요.
- 상단/하단 OSBar variant(`transparent`/`onFrameHigh`) — 선례는 둘 다 기본값
  (`transparent=false, onFrameHigh=false`)을 썼다. 동일하게 갈지 확인 필요.
- 선택 완료(하단 버튼 클릭) 후 이동할 화면·라우팅 — 선례는 목적지 화면(개통 신청서)이
  저장소에 없어 버튼 활성/비활성만 구현하고 실제 이동은 만들지 않았다. 이번에도 후속
  화면 계획이 없다면 동일하게 활성/비활성 전환까지만 구현하고 실제 이동은 범위 밖으로
  둔다 — 확인 필요.

### P2 — 선택, 근거 없음(확인 필요)

- 리스트가 비어 있을 때의 표현 (빈 상태) — 확인 필요.
- 로딩·에러 상태 표현 — 확인 필요.

## 성공 기준

이 저장소는 실사용자 데이터·분석 도구가 없으므로 비즈니스 KPI 대신, 이 저장소가 실제로
측정 가능한 산출물/품질 기준으로 성공을 판정한다.

- 페이지가 신규 컴포넌트 생성 없이 기존 5개 컴포넌트(`Header`, `Tab`, `ListRadio`,
  `OSBarTopNavigation`/`OSBarBottomNavigation`, `Button`)만으로 조립됐다.
- 토큰 스캔 기준 `src/` 내 raw 값(hex, px/rem 리터럴, Tailwind arbitrary value) 0건.
- `npm run typecheck` 통과.
- `npm run build` 통과.
- `npm run build-storybook` 통과 (스토리로 페이지 조립 상태를 확인할 경우).
- 키보드만으로 탭 전환·리스트 선택·하단 버튼 조작이 가능하고, 각 단계에서 포커스가
  시각적으로 표시된다.

## 리스크

- `Header`를 포함하기로 결정하면서 애초 추천됐던 "기존 4개 컴포넌트만" 범위가 5개로
  넓어졌다 — 의도된 확장이며, `Header`도 이미 다른 화면(Login/SignIn 등, 현재는 삭제됨)에서
  검증된 기존 컴포넌트이므로 신규 컴포넌트 생성에는 해당하지 않는다.
- 탭·리스트의 실제 콘텐츠(카테고리명, 항목명, 개수)가 정해지지 않은 채 목업으로 진행하면,
  실제 콘텐츠가 확정된 뒤 레이아웃 재작업이 필요할 수 있다 — 선례도 같은 이유로 목업
  데이터(`MOCK_PLANS`)를 썼다.
- **선택 완료 이후 이동할 화면이 이 저장소에 없다는 문제가 선례에서도 그대로 있었고
  해결되지 않은 채 남았다.** 이번 페이지도 같은 한계를 상속할 가능성이 크다 — 후속
  화면을 만들 계획이 없다면 "선택 완료" 버튼은 이번에도 활성/비활성 상태 전환까지만
  구현하고 실제 이동은 범위 밖으로 둔다.
- 과거 `Benefit` 페이지의 원본 PRD(`docs/prd-list`)는 페이지와 함께 이미 삭제되어 이번
  조사로도 복구되지 않았다 — 위 표의 구조·props·성공 기준은 `Benefit.design.md`에 남아있던
  요약을 근거로 재구성한 것이지, 원본 PRD 전문을 재확인한 것은 아니다.

## 확인 필요 목록 (요약)

`Header` 포함 5개.

**아직 남은 것**:

1. 탭 라벨·개수, 리스트 항목 문구·개수 — 선례 패턴(탭 3개 + 탭별 목업 리스트) 재사용 가능
   하나 최종 문구는 확인 필요.
2. 상단/하단 OSBar variant(`transparent`/`onFrameHigh`) — 선례는 둘 다 기본값을 썼다.
   이번에도 기본값으로 갈지 확인 필요.
3. 선택 완료 후 이동 경로/라우팅 — 선례도 목적지 화면이 없어 미구현으로 남겼다. 이번에
   후속 화면을 만들 계획이 없다면 동일하게 범위 밖으로 둔다.
4. 빈 상태·로딩·에러 상태 표현 필요 여부 — 선례도 Figma·PRD 어디에도 근거가 없어
   구현하지 않았다. 이번에도 근거가 없으면 동일하게 비목표로 둔다.
